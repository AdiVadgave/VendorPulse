VendorPulse MVP — Development Plan
1. What We Are Building
VendorPulse is not a chatbot. It is:

A workflow orchestrator that moves a governance cycle through defined stages
A document intelligence layer that generates briefs, minutes, and responses using Claude
A governance memory system that stores historical data across cycles
A human-approved automation assistant — AI suggests, humans approve
The product automates Shell's EGB/QBR governance cycle end-to-end: from scheduling through post-meeting analytics.

5. Standard Agent Response Contract
Every agent returns this exact shape — the frontend never parses raw AI text:


{
  "status": "success | failed | partial | pending_approval",
  "agent": "scheduling_agent",
  "summary": "Attendee refresh form generated for 9 stakeholders.",
  "data": {},
  "warnings": ["3 stakeholders have not responded"],
  "next_actions": ["APPROVE_INVITE", "SEND_REMINDER"],
  "requires_approval": true,
  "run_id": "uuid"
}
6. Workflow Engine (State Machine)
The workflow_state on each cycle only moves forward and only when prerequisites are met.


CYCLE_CREATED
    → ATTENDEE_REFRESH_SENT       (trigger: start scheduling)
    → AVAILABILITY_COLLECTED      (trigger: all key attendees responded)
    → MEETING_SCHEDULED           (trigger: organiser approved a slot)
    → SCORECARD_REQUEST_SENT      (trigger: organiser approves dispatch)
    → SCORECARD_COLLECTION        (trigger: at least 1 submission received)
    → SCORECARD_COMPILED          (trigger: deadline passed or manual compile)
    → INTERNAL_ALIGNMENT          (trigger: scorecard compiled)
    → VENDOR_PREP                 (trigger: alignment complete)
    → MEETING_IN_PROGRESS         (trigger: meeting started)
    → POST_MEETING_COMPLETE       (trigger: minutes approved)
    → ARCHIVED                    (trigger: manual)
Enforcement rules (examples):

Cannot send vendor brief before scorecard is compiled
Cannot generate meeting minutes before meeting notes exist
Cannot move to ARCHIVED without at least one approved action item log
The workflow engine is a simple Python class with can_transition(from_state, to_state) and transition(cycle_id, to_state). No LLM involvement here — pure deterministic logic.

8. Claude API Agent Pattern
Each agent follows this exact pattern:


class BaseAgent:
    def __init__(self, db_session, cycle_id):
        self.db = db_session
        self.cycle_id = cycle_id
        self.client = anthropic.Anthropic()

    async def run(self, user_action: str, context: dict) -> AgentResponse:
        # 1. Build tool definitions
        tools = self._get_tools()
        # 2. Call Claude with system prompt + tools
        # 3. Execute tool calls as Claude requests them
        # 4. Return structured AgentResponse
        # 5. Log to agent_runs table
What uses LLM (Claude):

Generating vendor brief narrative from scored data
Drafting 2-3 pushback response options
Extracting structured action items from pasted meeting notes
Generating meeting minutes from captured note items
Generating leadership briefing card insights
Generating change highlight summary
What is deterministic (no LLM):

Slot ranking algorithm (hard/soft constraints scoring)
Score validation (range check, comment requirement)
Outlier detection (standard deviation calculation)
Score averaging and compilation
Cycle-to-cycle score diff (simple delta calculation)
Alignment flag detection (spread >= 1.5 threshold)
Recurring issue detection (count query on issues table)
Trend chart data (pure DB aggregation)
Workflow state transitions
This split keeps the system reliable and avoids hallucination in critical paths.

9. Module-by-Module Plan
Module A — Meeting Scheduling & Coordination
Goal: Go from a blank cycle to a confirmed meeting invite with tracked RSVPs.

Steps:

User clicks "Start New Cycle" → creates cycle record in CYCLE_CREATED state
System loads attendees from previous cycle
Scheduling agent generates attendee refresh form (rendered as modal in UI — no external form)
User reviews and dispatches → state moves to ATTENDEE_REFRESH_SENT
Mock responses come in (simulated by pre-seeded data + a "Simulate Responses" button)
Attendee list is updated; new names added, old ones replaced
MockCalendarService returns availability for all confirmed attendees
Deterministic slot ranker runs:
Organiser + exec sponsor = hard constraint (slot invalid if they're blocked)
Score = (confirmed attendees / total) × 100 − conflict penalty − timezone penalty
Top 3 ranked slots shown with attendance breakdown table
Organiser clicks "Approve This Slot"
Invite draft is generated and shown in approval panel
"Send Invite" (mock) → MockEmailService stores to outbox → notification table updated
Confirmation tracker panel shows ACCEPTED / DECLINED / PENDING per attendee
Auto-nudge message generated for non-responders (shown in notifications)
UI components needed:

AttendeeRefreshPanel — shows current list, refresh form, response status
SlotRankingPanel — 3 slot cards with breakdown
InviteApprovalPanel — email preview + approve/reject
ConfirmationTracker — live table of RSVPs
Module B — Scorecard Collection & Validation
Goal: Collect, validate, flag outliers, and compile a final scorecard.

Steps:

Triggered after meeting is scheduled (can run in parallel)
Scorecard request form generated for each stakeholder (5 categories, 1–5 scale, comment field)
Dispatch shown in approval panel → "Send to 8 stakeholders" → MockEmailService
State moves to SCORECARD_REQUEST_SENT
Reminder schedule runs automatically (visible in notifications panel):
T-5 days: informational tone
T-2 days: deadline notice tone
T-day: escalation flag to organiser
Each submission goes through validation service (deterministic):
All required fields present?
Score 1–5 range?
Score = 1 or 5 → comment required
Flag if score deviates > 1.5 std deviations from group average (re-checked after each batch)
Invalid submissions trigger a correction request back to submitter
Scorecard collection status panel shows per-stakeholder submission status
On deadline or manual trigger → "Compile Scorecard"
Final scorecard table generated: per-stakeholder scores + averages + outlier flags
State moves to SCORECARD_COMPILED
Validation rules (in validation_service.py, purely deterministic):


score < 1 or score > 5       → ERROR: out of range
score == 1 or 5, no comment  → ERROR: comment required
|score - group_avg| > 1.5σ   → WARNING: outlier flagged
category missing              → ERROR: required field
UI components:

ScorecardDispatchPanel — approval for sending requests
SubmissionTracker — per-stakeholder status table with reminder history
CompiledScorecardTable — final table with outlier badges + averages row
Module C — Internal Alignment Call Support
Goal: Prepare the internal team for the EGB/QBR by surfacing what changed and capturing actions.

Steps:

Triggered after scorecard is compiled
Deterministic score diff engine compares current cycle vs previous cycle:
Delta ≥ 1 point per category → highlighted change
New issues not in prior cycle → flagged as new
Alignment flag engine: for each category, check spread between stakeholder scores:
Spread ≥ 1.5 points → generate flag question (e.g. "Technical Lead scores Delivery Quality at 2; Commercial Lead at 4 — resolve before vendor call")
Claude generates a 3-5 bullet "What Changed" summary from the diff data
Face-off model panel shows current Shell/Vendor role-name mappings
User can update any position via inline edit form
During/after internal call, coordinator pastes notes into text area
Claude extracts structured action items: description, owner (if mentioned), due date (if mentioned)
Action items added to action log with status = OPEN
State moves to INTERNAL_ALIGNMENT
UI components:

ChangeHighlightsPanel — bullet list of deltas, new issues
AlignmentFlagsPanel — list of divergence flags with prompt questions
FaceOffModelEditor — numbered grid, inline editable
NotesInputPanel — paste area + "Extract Actions" button
ActionLog — shared component used across modules C, D, E
Module D — Vendor Prep Call Support
Goal: Give the Shell team a ready vendor brief and manage pushback professionally.

Steps:

Triggered after internal alignment is complete
Claude generates vendor brief using tool calls to fetch:
Current scorecard averages
Category-level stakeholder comments
Previous cycle scores (for trend context)
Open action items from Module C
Output: structured brief with Overall Score, Per-Category Ratings + Rationale, Key Concerns, Positive Areas
Brief shown in approval panel — human reviews before vendor sees it
Vendor objection/pushback input form (free text + category selector):
Categories: DATA_DISPUTE, PROCESS_CONCERN, RESOURCE_CONSTRAINT, SCOPE_DISAGREEMENT, OTHER
For each pushback item, Claude drafts 3 response options:
Factual stance (data-backed, no judgment)
Neutral collaborative stance
Firm escalation stance
Items requiring legal/commercial review are flagged and excluded from AI drafts
Shell team reviews responses, selects or edits one
Unresolved items go to issue tracker with status = OPEN
Face-off model update and notes/action capture (same as Module C)
State moves to VENDOR_PREP
UI components:

VendorBriefPanel — structured brief card with approval button
PushbackInput — form to add objections
PushbackResponseCards — 3-option cards with select/edit
UnresolvedItemTracker — table with status badges
ActionLog — reused from Module C
Module E — EGB/QBR Live Meeting Support
Goal: Real-time capture during the meeting + automatic post-meeting artefact generation.

Steps:

At meeting start, show trend briefing card (generated by Module F's trend engine):
3-cycle score movement per category
Most improved / most concerning areas
Predicted areas of vendor challenge (based on recurring issues)
Live capture panel — facilitator logs items during meeting:
QUESTION (+ who raised it)
OBJECTION (+ category)
DECISION
APPRECIATION
ACTION ITEM
Each item is timestamped
Alternatively: paste full meeting transcript → Claude parses into structured items
"Generate Minutes" button → Claude produces:
Meeting metadata (date, attendees, cycle ref)
Executive summary (2-3 sentences)
Agenda summaries
Key decisions list
Q&A and objection log
Action items extracted
Minutes shown in approval panel
On approval, action items merged with existing open items from Modules C and D
Minutes available for copy-to-clipboard export
State moves to POST_MEETING_COMPLETE
UI components:

MeetingBriefingCard — pre-meeting summary (from analytics engine)
LiveCapturePanel — type-selector + text input + timestamped feed
TranscriptInput — paste-and-parse alternate mode
MeetingMinutesViewer — structured minutes display + copy button
ActionLog — final merged action log
Module F — Cross-Cycle Memory & Analytics Dashboard
Goal: Persistent institutional memory, trend charts, recurring issue detection, leadership briefs.

Steps (data-driven, no real-time actions needed):

All historical cycles auto-stored (4 pre-seeded cycles + any new cycles created)
Trend chart: per-vendor per-category line chart over cycles (Recharts LineChart)
Radar/spider chart: current vs previous cycle overall vendor health (Recharts RadarChart)
Cross-vendor bar chart: current cycle scores side-by-side
Recurring issue detection (deterministic):
Query issues table for same vendor: occurrences >= 2 AND status = OPEN
Display as red alert cards: "Delivery Quality flagged for 3 consecutive cycles — Vendor X"
Leadership briefing card (Claude-generated):
Input: trend data + recurring issues + prior unresolved items + prior agreements
Output: Vendor Trajectory (improving/stable/declining) + Unresolved Recurring Issues + Prior Commitments Requiring Follow-up + Recommended Focus Areas
Charts and brief accessible from main Analytics page and from within each cycle's module
UI components:

TrendLineChart — per-vendor per-category over time
RadarChart — current vs prior cycle
CrossVendorComparison — bar chart current cycle
RecurringIssueAlerts — alert card list
LeadershipBriefCard — 4-section card with "Generate" button

15. Key Design Decisions
Decision	Rationale
SQLite over Postgres	Zero-config, file-based, perfect for demo; schema-compatible with Postgres for production
Tool-calling agents over prompt-only	Better control, lower hallucination, easier debugging
Deterministic logic for validation and ranking	Explainable to a Shell executive audience; no AI "black box" for critical paths
Mock services behind interfaces	Swap to Outlook/Teams API later without rewriting agent code
Single JSON contract (AgentResponse)	Frontend never guesses shape; stable even as AI outputs evolve
Human approval before every "send" action	Builds client trust; legally important for governance context
Workflow state machine	Prevents impossible state combinations (can't generate minutes without notes)
Seed data tells a story	Demo analytics only work if the data has deliberate trends and recurring issues
