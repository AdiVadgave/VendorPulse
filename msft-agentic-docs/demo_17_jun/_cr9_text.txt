EGB/QBR Process Automation 
Shell currently runs vendor governance cycles (QBRs / EGBs) as a largely manual exercise, coordinators chase 
availability over email, scorecards arrive piecemeal across inboxes, alignment meetings recap the same recurring 
issues, and post-meeting minutes are inconsistent quarter on quarter. VendorPulse is an agentic AI platform that 
automates the orchestration end-to-end while keeping every outbound action (emails, invites, briefs, minutes) under 
human approval. The proof-of-concept already demonstrates the six-stage workflow against a Gmail/Google-Forms-
based mock environment. This document set scopes the work to lift that POC into a Shell-grade production 
deployment hosted in Shell's Azure tenant, integrated with Outlook + Teams, and removed entirely from Google's 
stack.

The following pages provide the full detail behind the change summarised in Part I above, 
covering scope, the four-week delivery plan (three development weeks plus a deployment and

1. Description of Changes 
VendorPulse will deliver the six capabilities (A-F) proven in the proof-of-concept, re-engineered 
onto a Shell-owned production platform. The functional behaviour validated in the POC is 
accepted as the baseline; this Change Request re-engineers the integration and platform layer 
beneath it. Three architectural invariants are preserved without alteration across all six 
capabilities: (1) the twelve-state, forward-only workflow state machine (CYCLE_CREATED -> 
ATTENDEE_REFRESH_SENT -> AVAILABILITY_COLLECTED -> 
MEETING_SCHEDULED -> SCORECARD_REQUEST_SENT -> 
SCORECARD_COLLECTION -> SCORECARD_COMPILED -> INTERNAL_ALIGNMENT 
-> VENDOR_PREP -> MEETING_IN_PROGRESS -> POST_MEETING_COMPLETE -> 
ARCHIVED); (2) the human-approval gate, whereby no email, invite, brief or set of minutes 
leaves the system without explicit coordinator approval in the UI; and (3) the "deterministic-first, 
AI-second" principle, whereby all business-critical logic (slot ranking, score validation, outlier 
detection, workflow transitions and audit) is deterministic Python, and the LLM is used solely to 
generate human-readable text (briefs, minutes, summaries and draft email bodies) that a person 
reviews before any action is taken. 
The single largest change common to capabilities A, B, C and E is the complete removal of the 
consumer Google stack used in the POC (the Gmail API operating from a developer's personal 
Google account, and the public Google Form polled every ~90 seconds) and its replacement with 
Microsoft Graph, Teams and Outlook operating from a dedicated Shell service mailbox under 
app-only certificate authentication, together with a native in-app scorecard form. The LLM 
provider sits behind a single abstraction so the choice between the Anthropic Claude API 
(recommended) and Azure OpenAI is a configuration setting, not a code change. The per-
capability detail below sets out what each capability does, the specific POC-to-production 
change, the deterministic-versus-AI split, and the approval gate. 
A. Meeting Scheduling & Coordination 
This capability refreshes the attendee roster from the Shell directory, sends attendance-
confirmation outreach to participants, queries candidate times against real Shell mailboxes using 
the Graph findMeetingTimes endpoint, deterministically ranks the resulting slots, creates the 
Microsoft Teams meeting and dispatches the calendar invite, and tracks RSVPs. Slot ranking 
applies a hard constraint that the organiser and the executive sponsor must both be free, with soft 
scoring on attendance percentage, calendar conflicts and timezone fit. 
In production, all directory lookups, free/busy queries, meeting creation and invites move to 
Microsoft Graph using app-only certificate authentication from the Shell service mailbox, 
replacing the POC's single short-lived delegated bearer token pasted into a .env file. The Teams 
online meeting and the invite are created through Graph rather than any Google service. Slot 
ranking, the organiser/sponsor hard constraint, all soft scoring and the RSVP state tracking 
remain fully deterministic Python; the LLM is not involved in selecting or scoring times. The

only AI contribution is optional polishing of outreach text. The invite is created and sent only 
after the coordinator approves the proposed slot and message in the UI; until then no calendar 
action is taken. 
B. Scorecard Input Collection & Validation 
This capability issues personalised scorecard requests to key stakeholders, collects their ratings 
on a 1-5 scale across four categories and sixteen parameters (Risk & Compliance, Performance, 
Commercial, Relationship), runs escalating reminders for non-responders, validates the 
submissions deterministically, and compiles the internal-stakeholder-versus-vendor scorecard. 
Validation enforces the 1-5 range, requires a mandatory comment for extreme scores of 1 or 5, 
and flags statistical outliers at approximately 1.5 standard deviations. 
The POC collected responses through a public Google Form polled on a timer; in production this 
is removed entirely and replaced by a native in-app form persisted in Azure PostgreSQL, giving 
Shell full ownership of the data and removing the external dependency and polling latency. 
Scorecard request emails and reminders are issued via Graph mail from the service mailbox 
rather than Gmail. All validation logic (range checking, mandatory-comment enforcement, ~1.5-
sigma outlier flagging) and the compilation of the comparative scorecard remain deterministic; 
the LLM performs no part of scorecard scoring or validation. As no outbound communication is 
involved in collection itself, the approval gate applies to the request and reminder emails, which 
the coordinator approves before dispatch. 
C. Internal Alignment Calls Support 
This capability supports the internal alignment call by computing score deltas against the 
previous cycle, flagging categories where the internal and vendor views diverge by a spread of 
1.5 or more, drafting a narrative explanation of what changed, extracting action items from raw 
alignment-meeting notes, and scheduling an internal-only Teams alignment meeting. 
In production the internal alignment meeting is scheduled via Microsoft Graph as a Teams 
meeting from the service mailbox, replacing any POC-era external scheduling. The delta 
calculation and the divergence flagging (spread >= 1.5) are deterministic. The LLM is used only 
to draft the "what changed" narrative and to extract candidate action items from unstructured 
notes; both outputs are presented to the coordinator for review and editing, and the alignment 
meeting invite is issued only after coordinator approval. 
D. Vendor Prep Call Support 
This capability prepares the team for the vendor preparation call. It generates an AI vendor brief 
covering the overall score and trend, per-category ratings, key concerns, positive areas and open 
actions, and drafts three distinct response stances (Factual, Neutral and Escalation) for each 
anticipated vendor pushback item, while tracking unresolved items through the cycle. 
The vendor brief and the three-stance response drafts are LLM-generated human-readable text; 
the underlying scores, trends and open-action data they summarise are produced 
deterministically. A deterministic guardrail suppresses AI drafting entirely for any item flagged 
for legal review, so that no machine-generated response is offered on legally sensitive matters. 
This capability is internal-facing and produces no outbound communication of its own; the brief 
and drafts are advisory material that the coordinator and prep team review and adapt. As with all 
capabilities, any item that subsequently results in an outbound message is subject to the human-

approval gate. In production this capability runs against data held in Azure PostgreSQL and the 
chosen enterprise LLM under a zero-retention, no-training, EU-residency DPA. 
E. EGB/QBR Combined Meeting Support 
This capability supports the combined EGB/QBR meeting itself. It produces a pre-meeting 
facilitator briefing, captures live notes during the meeting under five types (Question, Objection, 
Decision, Appreciation, Action), parses a pasted transcript into structured notes, generates formal 
meeting minutes, extracts action items, and distributes the approved minutes to internal 
stakeholders. 
The production change is that approved minutes are distributed via Graph mail from the Shell 
service mailbox, replacing the POC's use of the Gmail API from a personal account. The LLM 
parses the transcript into structured notes and drafts the facilitator briefing and the formal 
minutes; the five-type note classification, the action-item register and the workflow state advance 
remain deterministic. The minutes are explicitly held behind the human-approval gate: the 
coordinator reviews and approves the generated minutes before they are distributed, and no 
minutes are sent automatically. Note that ingestion of live Microsoft Teams transcripts is out of 
scope for the first release; transcripts are pasted in for parsing. 
F. Cross-Cycle Memory & Trend Analysis 
This capability provides longitudinal intelligence across cycles. It surfaces multi-cycle score 
trends, detects recurring issues (defined as a category remaining below threshold for two or more 
consecutive cycles), classifies each vendor's trajectory as improving, stable or declining, 
produces an executive leadership brief, and generates a cross-vendor comparison. 
All trend computation, recurring-issue detection and trajectory classification are deterministic 
and run over the cycle history now held in Azure PostgreSQL rather than the flat JSON files 
used in the POC; persisting history in a managed database is the principal production change for 
this capability and is what makes cross-cycle memory reliable at Shell scale. The LLM 
contributes only the human-readable executive leadership brief. This capability is read-only and 
analytical and produces no outbound communication, so it raises no new approval-gate or 
external-integration surface; any leadership brief shared externally would follow the standard 
approval gate. 
2. Capabilities / Features of the Agent 
In addition to the six functional modules described elsewhere in this proposal, VendorPulse 
provides a set of cross-cutting, system-wide capabilities that define the production platform. 
These are the traits that distinguish the Shell-grade production system from the proof-of-concept: 
how it authenticates, how it integrates with Microsoft 365, how it applies AI safely, and how it 
remains governed, auditable and operable by Shell IT Ops. The functional behaviour of Modules 
A–F is accepted as the baseline; the capabilities set out below describe the enterprise platform 
layer that will host that behaviour. Two of these capabilities are forward-looking build targets 
correctly aligned to the production design but not yet present in the POC code — the 
recommended Anthropic Claude provider path and the 4-category / 16-parameter scorecard 
taxonomy — and each is called out below so that a technical reviewer comparing this proposal to 
the current repository sees no gap between what is claimed and what exists today. 
Security & Identity

•  Entra ID Single Sign-On: users authenticate through Shell's Entra ID (Azure AD) using 
OIDC. There are no application-managed passwords; access follows Shell's existing identity,

•  Microsoft Graph for all messaging and scheduling: attendance outreach, scorecard requests,

AI & Determinism

deterministic Python. Outcomes are reproducible and explainable, and do not depend on

•  AI confined to text generation: the LLM is used only to produce human-readable text —

3. Out of Scope 
The first production release of VendorPulse is deliberately scoped to deliver the six governance 
capabilities (Modules A–F) end-to-end as a Shell-owned, Shell-grade system within the four-
week plan and a single pilot vendor cycle. To safeguard that timeline and outcome, the items 
below are explicitly out of scope for this release. Their exclusion does not reflect a technical 
constraint of the platform; each is a deliberate sequencing decision. Items are organised into (1) 
core functional exclusions and (2) capabilities deferred to the warranty period or a subsequent 
statement of work (SOW).

7. Risks 
Risk Overview 
The defining characteristic of this engagement is its compressed four-week (20 working-day) 
sprint with no Phase-0 buffer. The plan is feasible only on the explicit assumption that Shell 
completes all pre-mobilisation access provisioning - Entra app registrations and admin consent, 
the service mailbox and Application Access Policy, the full Azure estate (including egress allow-
listing and private endpoints), the LLM provider contract, DNS/TLS, and repository/CI-CD 
guest access - before Day 1, and that the Zensar team is 100% allocated with no planned leave. 
As a consequence, the principal risks to the engagement are not technical-build risks (the six 
modules are an accepted POC baseline) but dependency-readiness and access risks: any 
prerequisite that arrives late converts directly into lost delivery days, and on a 20-day plan there 
is little slack to absorb slippage. 
Risks are grouped below into five categories: (1) Zensar delivery-tooling and velocity risks; (2) 
Microsoft identity, Graph and messaging risks; (3) Azure platform, networking and cutover 
risks; (4) LLM provider and compliance risks; and (5) scope, schedule and quality risks. The

consolidated risk register that follows scores each risk by likelihood and impact, states the agreed 
mitigation, and names the accountable owner. A note on likelihood ratings: items that are wholly 
within Zensar's control during pre-mobilisation (developer laptops, IDE approval, Claude Code / 
Anthropic licences) are rated Low likelihood and are managed as pre-contract go/no-go gates 
rather than open delivery risks; their impact remains High because, were a gate missed, the AI-
accelerated plan could not start. 
Risk Categories 
1. Zensar delivery-tooling and AI-accelerated velocity 
The four-week schedule is predicated on AI-assisted (pair-programming) development. If the 
enabling tooling is not in place on Day 1, delivery velocity is lost and the plan slips immediately 
- there is no recovery window. These risks are entirely controllable in pre-mobilisation and are 
therefore treated as go/no-go gates before contract start, which is why they carry Low likelihood 
despite a High impact. 
•  Developer laptops: if every engineer is not equipped with a full local dev environment 
(Python 3.11+, Node.js, Docker Desktop, Git) and admin rights, the team cannot build or run 
the system from Day 1. Likelihood Low - Zensar-controlled and treated as a pre-contract 
go/no-go gate. 
•  IDE approval: if VS Code (or JetBrains) and required extensions are not Shell-approved, 
engineers lack sanctioned tooling and lose time on workarounds. Likelihood Low - Zensar-
controlled go/no-go gate. 
•  Claude Code / Anthropic developer licences: if Claude for Work licences and an Anthropic 
API developer key are not procured, the AI-assisted development that the compressed 
schedule depends on is unavailable, and the four-week plan slips. Likelihood Low - Zensar-
controlled go/no-go gate. 
•  Network access / VPN / device compliance: if engineers cannot reach Shell's Azure tenant, 
repo and non-prod Graph from their laptops, no integration work can proceed. 
•  Source control + CI/CD guest onboarding: if engineers are not added as guests to Azure 
DevOps / GitHub Enterprise with branch protection and a CI/CD service principal, code 
cannot be merged or deployed. Guest onboarding is flagged as a 3-7 day item that can be 
slow, and it blocks the Day-1 branch-and-scrub task as well as all subsequent deployments. 
2. Microsoft identity, Graph and messaging 
Modules A (Scheduling) and B (Scorecard), and the outbound actions in C and E, depend 
entirely on Microsoft Graph app-only authentication from the service mailbox. The Entra admin-
consent process is the single longest lead-time item (a 2-4 week security review) and is the 
critical path for the whole engagement. Crucially, admin consent and the mailbox-scoping 
Application Access Policy are not independent: Shell security is expected to require the 
Application Access Policy as a precondition for granting tenant-wide app-only Mail.Send / 
Calendars permissions, so the two must be treated as a single coupled security-review package. 
•  Graph app-only admin consent (Mail.Send, Calendars.ReadWrite, 
OnlineMeetings.ReadWrite.All, User.Read.All, MailboxSettings.Read, Group.Read.All) not 
granted in time: Modules A and B cannot be delivered on real Graph. This is the long pole - it 
must be started ~4-6 weeks ahead. 
•  Application Access Policy not offered or not accepted, so tenant-wide app-only consent is 
refused: if the mailbox-scoped policy is not proposed up front, security may reject the consent

request as too broad, stalling or blocking Modules A & B. The policy and the consent request 
must be submitted together as a least-privilege package. 
•  Service mailbox / Application Access Policy not provisioned or mis-scoped: the dedicated 
vendorpulse-svc mailbox cannot send mail or host Teams meetings (blocking Modules A, B, 
C and E), or the consent is refused because the scope is too broad. Provision the mailbox with 
an E3/E5 licence and apply the policy scoping Mail.Send / Calendars in pre-mobilisation. 
•  Graph certificate not generated, uploaded or rotated in time (or a client-secret used against 
Shell's stated preference for certificate credentials): app-only Graph auth cannot be 
established, blocking all email/calendar/Teams traffic. Agree certificate ownership (Shell-
generated preferred), thumbprint handover, Key Vault certificate storage and a 12-month 
auto-renewal rotation in pre-mobilisation. 
•  Graph API throttling (429 / 5xx): findMeetingTimes and mail-send calls intermittently fail; 
mitigated by the retry/backoff already engineered into GraphService. 
•  Conditional Access blocking the service principal: the service mailbox cannot authenticate, 
blocking all outbound A & B actions; requires a CA exemption or a confirmed sign-in path 
agreed with the Entra admin. 
•  External / guest meeting policy blocking vendor invites: if the service mailbox cannot invite 
external vendor attendees, Teams invites for the QBR cannot be issued. 
3. Azure platform, networking and production cutover 
•  No SQL schema yet and messy POC SQLite/JSON data: the current POC persists ~13 
entities as flat JSON/SQLite; these migrate to ~15 PostgreSQL tables (asyncpg, Alembic). 
The migration and data cleansing overrun Week 1 if data quality is poor; mitigated by scoping 
cleansing up front, providing defaults for missing fields, and committing to additive-only 
migrations after the Day-10 code freeze so the schema is effectively frozen. 
•  Outbound egress / NAT allow-listing to Graph and the LLM endpoints not configured: a 3-
7 day networking item flagged as a possible hidden long pole. If not in place, all Graph and 
LLM calls fail from inside the VNet at runtime. Agree the egress allow-list (Graph plus the 
Anthropic / Azure OpenAI endpoints) with Shell Networking in pre-mobilisation and validate 
connectivity from non-prod in Week 1. 
•  Private endpoints / VNet integration to PostgreSQL and Key Vault not in place: the 
application cannot retrieve secrets via Managed Identity or reach the database at start-up. 
Provision private endpoints, VNet integration and Managed Identity role assignments in pre-
mobilisation and smoke-test secret retrieval and DB connectivity on Day 1. 
•  DNS / TLS cutover failure in Week 4: the production cutover (DNS, slot-swap, 60-minute 
observation) fails; mitigated by provisioning DNS+TLS in pre-mobilisation and a tested 
rollback via slot-swap. 
•  Azure estate incomplete (RGs, Postgres, Key Vault, App Service, Front Door + WAF, App 
Insights, Managed Identity role assignments, egress allow-listing): foundation work in Week 
1 cannot complete. 
4. LLM provider and data compliance

LLM for briefs, minutes, summaries and draft email bodies) are blocked or non-compliant. 
Procurement and Legal must start 4-8 weeks ahead. 
•  Azure OpenAI quota / region approval not granted (if Azure OpenAI is chosen as the 
provider): the fallback LLM provider is unavailable, eliminating the config-only switch that

•  Azure OpenAI deployment misconfigured (a preview or non-chat / computer-use 
deployment rather than a gpt-4o-class chat deployment): LLM tool-calling fails. 
•  LLM token-spend overrun: monthly budget exceeded; mitigated by token-budget guards,

block cutover; mitigated by engaging the Security liaison from Day 1.
